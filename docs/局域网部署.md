# ubuntu24 局域网网关部署

当前状态：**代码交付；未迁移 ubuntu24，未标记“局域网访问已上线”**。

目标为 `http://192.168.9.202:8000`。设备先通过 Caddy Basic Auth，再进入原应用登录界面。Basic Auth 使用 HTTP 明文传输，只适用于可信局域网；本次没有 HTTPS、自动证书、公网发布或路由器转发。

## 文件与认证

- `compose.lan.yaml` 单独运行，项目固定为 `goofish-monitor`，原服务仍为 `app`。**禁止与 compose.local.yaml 或默认 Compose 文件叠加。**
- app 不发布宿主机端口；默认网络保留外网访问能力，不使用 `internal: true`。原有九项挂载路径不变，数据库仍为 `/app/data/app.sqlite3`。
- gateway 使用官方 `caddy:2.11.2-alpine@sha256:834468128c7696cec0ceea6172f7d692daf645ae51983ca76e39da54a97c570d`，Cloud 已实际拉取并运行。监听 `http://:80`；所有路径统一认证，含 API、认证接口、WebSocket、静态资源、文档与健康检查。
- `.lan/gateway.env`：0600，保存 LAN IP、端口、用户名、bcrypt 哈希、原应用 digest、原容器名、共享内存及日志轮转参数。脱敏格式见 `deploy/lan/gateway.env.example`。
- `.lan/credentials.json`：0600，保存随机生成的独立网关明文密码（36 字节随机源）和用户名；默认用户名 `lanadmin`。仅本人通过不记录内容的安全编辑器读取，勿 `cat` 到终端、聊天或日志。应用 `.env` 中的用户名、密码、模型与通知设置不变。
- `.lan/`、`.lan-backups/` 权限 0700，均忽略提交。文件使用独占创建，不覆盖已有配置或重新生成已有凭据。若只存在两个凭据文件中的一个，停止并要求人工恢复，避免意外更换密码。
- bcrypt 由 Caddy 通过标准输入生成，明文不进入进程参数。env 文件中的值使用单引号保留 `$`；`compose config` 的导出表示会将 `$` 写成 `$$`。脚本同时验证导出格式及实际容器环境中的原始哈希。不要把导出的 `$$` 手动回写到 gateway.env。
- 两个服务自动重启且排除 Watchtower。app 使用 init 回收进程，沿用原共享内存和 json-file 的 max-size/max-file；旧部署未设轮转时补为 10m/3。Caddy 也使用 10m/3 日志轮转，不开启访问日志。gateway 的 NO_PROXY 包含 app，避免内网反代被 Docker 默认代理截获。

## 前提与停止条件

在 **ubuntu24 本机**，由能访问本地 Docker、读取部署数据、创建受限备份的用户执行。依赖 Python 3.10+（标准库）、Docker Engine、Docker Compose v2（支持 `config --format json`）、iproute2 的 `ip` 和 `ss`；Cloud 实测 Compose 2.40.3。脚本显式使用本地 unix:///var/run/docker.sock，清除 Docker 远程 context/TLS 选择变量，保留 registry 凭据与代理配置。

预检查以 `/home/o0521/ai-goofish-monitor/compose.local.yaml` 和实际容器标签为依据，不把 GitHub 默认 Compose 当作服务器配置。要求：

1. 原项目仅有运行中的 app，原绑定为 `127.0.0.1:8000:8000`，运行目录与旧 Compose 路径相符。
2. 九项挂载及现存文件/目录完整，已有 SQLite 数据库通过 quick_check。没有路径时停止，不新建空配置或数据库。
3. 从正在使用的 image ID 查找 RepoDigest，锁定原镜像，不拉取、构建或升级应用。
4. `192.168.9.202` 确实属于本机。8000 被本项目占用可迁移，被其他 Docker 项目或本机进程占用则停止，不改端口、不终止对方。
5. 原 app 已启用 init、Watchtower 排除；日志驱动为 json-file。额外 command、entrypoint、健康检查、资源/安全配置、标签、自定义网络或其他服务会导致预检查拒绝，须本地 Codex 先审查并在新文件中明确保留，不能删除原设置绕过检查。
6. **原界面中先停止运行任务、暂停所有启用的 cron 定时任务。** 应用启动会恢复调度，脚本为避免抓取而拒绝存在这些任务的数据库，不自行修改任务。部署和验收期间不创建/启动任务、不调用 AI、不发送测试通知。
7. 旧 Compose 展开的环境必须与新配置完全一致（含 APP_DATABASE_FILE）；若原文件有 `.env` 以外的覆盖值，脚本拒绝丢弃，需先在本地核对并适配，切勿打印包含秘密的配置。

运行 `precheck` 不停服务、不生成密码；为并发锁创建 `.lan`，并在已有网关配置时运行一次性 Caddy 校验容器。脚本失败时隐藏子命令输出，因为 Compose 报错可能包含敏感值。不要用 `set -x`、`docker inspect` 全量输出或 `docker compose config` 输出到公开日志调试；应在受限文件中检查。

## 首次安装与迁移命令

下列命令由本地 Codex 在 ubuntu24 执行。先核对当前目录和权限，不需要 Cloud 访问私有 IP。不切换服务器应用代码分支，只取本次新增部署文件；`--keep-old-files` 确保不覆盖已存在的自定义部署文件。已有同名文件时会停止，先比较并保留用户修改，再继续。

```bash
set -euo pipefail
cd /home/o0521/ai-goofish-monitor
git fetch origin feat/lan-access-gateway
git archive FETCH_HEAD compose.lan.yaml deploy/lan scripts/lan.py | tar --extract --keep-old-files
python3 scripts/lan.py precheck --directory /home/o0521/ai-goofish-monitor --old-compose compose.local.yaml
python3 scripts/lan.py apply --directory /home/o0521/ai-goofish-monitor --old-compose compose.local.yaml
python3 scripts/lan.py verify --directory /home/o0521/ai-goofish-monitor --old-compose compose.local.yaml
```

应用操作流程：

1. 拉取固定 digest 的 Caddy；检查实际旧部署与现有数据。
2. 将原 Compose 展开为受限的 `rollback.compose.json`，把应用 image 固定到正在运行的 digest，禁止回滚时拉取镜像。保留原 compose.local.yaml 不改写。
3. 停止本项目 app；再检查数据库与任务，创建 `.lan-backups/<UTC时间>/preserved.tar.gz`。包含 `.env`、`data/`（含数据库与 WAL 等）、`state/`、`prompts/`、`logs/`、`images/`、`jsonl/`、`price_history/`、`config.json` 和旧 Compose 文件。备份失败立即用锁定镜像的旧配置恢复，不继续迁移。
4. 记录全部 SQLite 表的行数及 .env/config/state/prompts 的 SHA256，仅保存在受限基线文件；生成凭据（如已存在则复用），校验展开配置和真实 Caddy 配置、容器哈希。
5. 使用独立 compose.lan.yaml 启动新服务，Caddy 接管指定 IP 的 8000。原 app 不再发布端口。
6. 验证无认证/错误密码返回 401、正确密码访问主页及 /health、端口发布正确、数据库各表计数与配置哈希一致。任何失败恢复旧服务，默认不覆盖数据库。

脚本成功仍只意味着服务器本机检查通过。必须完成另一台局域网设备验收，才能记录“局域网访问已上线”。再次运行 `apply` 会先核验已有部署，再验证，不重置凭据、不重复备份、不重启服务。若上次已自动回滚，迁移日志会保留以阻止盲目重试；本地 Codex 先检查原因与旧服务状态，保留归档日志后再重试，勿删除网关凭据与备份。

## 日常运行与回滚

正常重启（不要使用仓库默认 Compose）：

```bash
cd /home/o0521/ai-goofish-monitor
docker compose --env-file .lan/gateway.env -f compose.lan.yaml -p goofish-monitor restart app gateway
python3 scripts/lan.py verify --directory /home/o0521/ai-goofish-monitor
```

运行 `restart` 及验收前保持任务暂停，避免应用调度启动真实采集。应用侧定时任务以后何时恢复由用户决定，不属于本次验收。

手动回滚：

```bash
cd /home/o0521/ai-goofish-monitor
python3 scripts/lan.py rollback --directory /home/o0521/ai-goofish-monitor --old-compose compose.local.yaml
```

回滚停止本项目新服务、移除本项目 gateway 容器，恢复后检查原 127.0.0.1 端口的 /health，以 `.lan/migration.json` 指向的受限 `rollback.compose.json` 恢复原 app（仅 127.0.0.1:8000 发布，原 image digest）。原 Compose 和所有备份均保留。此解析后配置含环境秘密，禁止提交或公开。

若在写迁移日志前备份/校验失败，脚本直接用本次备份目录中的 rollback.compose.json 恢复。若自动恢复也失败，脚本明确报告；本地 Codex 读取最新受限备份路径，检查实际容器后手工运行：

```bash
# 用实际本次备份时间替换 <UTC时间>；不要选择其他项目。
docker compose --project-directory /home/o0521/ai-goofish-monitor -p goofish-monitor \
  -f /home/o0521/ai-goofish-monitor/.lan-backups/<UTC时间>/rollback.compose.json \
  up -d --pull never --no-build app
```

此操作前如 gateway 仍占用目标端口，先用 compose.lan.yaml **只停止本项目服务并移除 gateway**。不要执行 `down -v`、`docker system prune`、全局清理、重建数据库或解压备份覆盖现有数据。数据库恢复属于单独的人工灾难恢复流程，本次无数据库迁移。

## 防火墙诊断

不自动改 UFW、nftables、iptables、Docker 守护进程或全局路由。服务器本机 verify 成功而其他设备连接失败时，由本地 Codex 读取 `ip -4 addr`、`ip route`、`sudo ufw status numbered`、`sudo iptables -S DOCKER-USER` 或对应 nftables 规则，结合客户端来源 IP 与规则计数找出阻断位置，报告原因及匹配到的规则，不猜测掩码或接口。

例如**仅当实际接口为 enp3s0、实际子网确认为 192.168.9.0/24 且阻断位于 UFW INPUT**时，所需精确规则为：

```bash
sudo ufw allow in on enp3s0 proto tcp from 192.168.9.0/24 to 192.168.9.202 port 8000
```

这是有条件的规则示例，不能未经诊断照抄。Docker 发布端口常走 FORWARD/DOCKER-USER 而不走 UFW INPUT；若实际阻断在 DOCKER-USER，报告只允许实际 LAN 入接口、实际来源子网、TCP、conntrack 原始目标 192.168.9.202:8000 的精确 ACCEPT 插入规则及其位置，由用户在本次网络配置边界外决定。不得关闭防火墙或放行任意来源。没有局域网客户端证据时，报告“外部可达性待验收”，不能声称防火墙已通过。
